Section 1
Chat Enhancement Prompt
Drives the structured, option-based travel planning conversation with a strict JSON contract, multi-step flow, destination validation, date parsing, and guest/room confirmation. Well-structured and on-brand, but contains two critical issues and three design-level warnings.

Critical Issues
Critical Missing catch-all / fallback branch ▾
The prompt defines JSON format for option-selection steps and an invalid-destination handler, but provides no instruction for messages that fall outside all defined branches — for example, a plain greeting, a non-travel question, or an ambiguous message mid-flow. The model will improvise both format and content, silently breaking the JSON contract.
RecommendationAdd an explicit rule at the end of the prompt: "For any user message that does not match a defined step or condition above, respond with: {"description": "<warm redirection>", "options": []}."
Critical Template variables left un-resolved ▾
The prompt contains JavaScript template literals — ${date}, ${destinations.map(...)} — that must be interpolated server-side before the string is sent to the model API. If the runtime skips this step, the model receives literal dollar-brace tokens and cannot function correctly: it has no date context, no destinations list, and no knowledge of what constitutes a valid destination.
RecommendationAdd a pre-flight assertion in your prompt-builder service that throws an error if any ${...} token remains in the resolved string. Log the full prompt in staging to verify injection on every deployment.
Warnings
Warning Date parsing section is over-specified ▾
The date intelligence block spans five pages and enumerates dozens of format patterns. LLMs handle date parsing well under shorter principle-based instructions. Over-specification increases token consumption per request, raises cost at scale, and paradoxically increases fragility — the model may enter pattern-matching mode and fail on formats not explicitly listed (e.g. "a fortnight from now", regional formats like "15.3.26").
RecommendationCollapse to 6–8 principle-based lines: default to DD/MM/YYYY; if year is omitted use the next upcoming occurrence; if only a start date is found, ask for duration. Let the model's native date reasoning handle the rest.
Warning Conversation flow not enforced — model can skip steps ▾
Steps 1–3 are presented as guidance examples rather than enforced state-machine rules. Nothing in the prompt prevents the model from advancing from destination selection directly to date collection, bypassing the experience-type step entirely. In practice this means a subset of users will receive an incomplete experience selection, corrupting downstream itinerary personalisation.
RecommendationAdd an explicit gate: "Do NOT advance to step N+1 until the user has provided a valid response to step N. If the user message is ambiguous or off-topic, re-ask the current step question."
Warning Ticker / preset phrase matching is brittle ▾
The four preset patterns rely on exact-match string recognition. Any variation in capitalisation, spacing ("50 +" vs "50+"), punctuation, or synonym use ("Journey", "Trip", "Experience") will silently fall through to normal flow handling instead of triggering the preset branch — creating an inconsistent experience for users arriving via marketing tickers.
RecommendationReplace exact-match instructions with intent-based language: "If the message conveys that the user has pre-selected a destination in the context of a Greytt 50+ adventure (in any phrasing), treat it as a direct destination selection and skip to the experience step."
What Is Working Well
Good Invalid destination fallback ▾
The handling of unrecognised destinations is clear, complete, and on-brand. The copy acknowledges the user's choice warmly before redirecting — exactly the right tone for a 50+ travel audience. Worth preserving verbatim in future iterations.
Good Guest and room confirmation pattern ▾
Defaulting to "2 Adults, 1 Room" with a confirm/customise binary choice is smart UX — it reduces interaction steps for the statistical majority of users while keeping customisation accessible. This pattern should be reused wherever sensible defaults exist.
Section 2
Voice Concierge Prompt
Contains two distinct prompts: a Chat System Prompt for conversational flow and an Extraction System Prompt for structured data retrieval. Both serve Greytt's voice-first experience but carry a fundamental architectural issue and several design risks.

Critical Issues
Critical Two prompts with conflicting output contracts in one document ▾
The Chat System Prompt instructs the model to respond in spoken prose with no markdown and no JSON. The Extraction System Prompt instructs it to output structured JSON data. These are intended for separate API calls but are concatenated in a single document. If sent together as one system prompt, the model receives directly contradictory instructions and will produce unpredictable output.
RecommendationPhysically separate into two distinct files/strings. Route to two independent API calls — one for conversational turns, one triggered after the conversation concludes to extract structured trip data from the full message history.
Critical ${PREFERENCE_DETAILS} variable is undefined ▾
The Extraction Prompt references ${PREFERENCE_DETAILS} to list available preferences and their sub-preferences — a critical dependency for correct extraction. This variable is not defined anywhere in the document. The extraction model currently has no preference taxonomy to map against and will either hallucinate categories or return empty preference arrays.
RecommendationDocument all runtime-injected variables in a prompt manifest. Populate ${PREFERENCE_DETAILS} with the full taxonomy before shipping, or add a guard that prevents the extraction call if this variable is empty.
Warnings
Warning isComplete threshold creates a hallucination incentive ▾
Requiring a minimum of five parent preferences before setting isComplete: true means the model is implicitly incentivised to infer — and potentially fabricate — additional preferences to satisfy the threshold when a user has only expressed two or three. These hallucinated preferences will flow silently into the itinerary engine with no flag, degrading recommendation quality in ways that are difficult to detect.
RecommendationRemove the count threshold. Return isComplete: false alongside a missingFields array listing what is absent. Let the backend or UI decide whether to prompt for more, proceed with partial data, or apply defaults.
Warning No off-topic guardrail in the chat prompt ▾
The Chat System Prompt has no instruction to redirect clearly off-topic queries. A user who asks about exchange rate apps, geopolitics, or medical advice will receive a warm, chatty response from Greytt with no redirection to travel planning. For a voice interface this is particularly risky — the conversation can drift far from the booking funnel with no recovery mechanism.
RecommendationAdd a soft redirect rule: "If the user's message is clearly unrelated to travel planning, briefly acknowledge it and gently steer back — e.g. 'That's a great question! Let's save that for another time — tell me more about where you'd love to travel.'"
Warning No missingFields output from extraction layer ▾
The extraction prompt outputs isComplete as a binary flag but provides no structured list of what fields are actually missing when isComplete is false. This forces downstream systems to re-parse the full conversation or make assumptions about which data is absent — increasing coupling between the AI layer and the booking engine.
RecommendationAdd a missingFields array to the extraction output schema: e.g. ["toDate", "rooms", "preferences"]. Downstream systems can then selectively prompt only for missing data without re-running the full extraction.
What Is Working Well
Good Conciseness rule is strong and voice-appropriate ▾
"Respond in 1 or 2 SHORT sentences. NEVER exceed 2 sentences." is a strong, measurable constraint well-suited for voice output where long responses feel unnatural. Paired with the spoken-word filler instruction, this will produce a distinctly human-sounding voice persona.
Good Destination fallback consistent across both prompts ▾
Both prompts use the same graceful invalid-destination handling — acknowledging the user's choice, noting it is coming soon, and redirecting to available options. Cross-prompt consistency here reduces confusion and reinforces the Greytt brand voice.
